# Lessons

What a person needs to understand to have written this application: the
physics it models, the algorithms it runs, and the languages and platform it is
built on. This file is the syllabus. It says which lessons exist or are to be
written, why each one matters to the application, what to read first, which
terms each one defines, and where in the code the idea lives.

## Two kinds of lesson

**Concept lessons** are written from this syllabus for a reader who has not done
the work. Each supplies its own concrete case first — a worked example with real
Kerbal numbers — then states the general idea, then shows the code that carries
it, and ends with a few questions to answer from memory and one thing to try in
the repository. They are living documents: revised when the code moves, filed
without a hash, with an _as of_ line inside naming the commit they were last
checked against.

**Moment lessons** are written by the `teach-lesson` skill right after a piece of
non-trivial work, for the person who just did it. They are short, dated by the
commit hash in their filename, and never revised. They are case studies; where
one illustrates a concept below, it links to that concept's lesson.

Both kinds file under the same tree, `docs/lessons/<category>/<topic>/`, with the
categories `physics`, `solver`, `renderer`, `ui`, `architecture`,
`verification`, `part-data` and `typescript`. The tree is for browsing by
principle. The four parts below are the reading order across it.

## How to read the tables

Each row is one lesson. _Because_ says what the application could not do
without the idea — that is the reason to learn it. _Needs_ lists the lessons to
read first; a _Needs_ that points forward means jump ahead and come back.
_Defines_ lists the terms the lesson introduces, each with a gloss of a few
words, so that this file defines every term at its first use and the lesson
gives the full definition. _Where_ names the code. A ★ marks the core: the rows
to read if you read nothing else.

**How the list changes.** Row numbers are identifiers: never renumbered, never
reused. A new row takes the next number in its part and sits where it belongs
in the reading order, so P26 may sit between P9 and P10. A row's title becomes
a link once its lesson is written. A row marked `(proposed)` was added outside
a review — by a moment lesson that found no row for its concept, or by a sweep
of the rules files and the code for what the syllabus does not yet teach — and
is accepted by deleting the marker or struck. The `teach-lesson` skill's
_Growing the syllabus_ section has the procedure. A ★ is given only in review.

**The rule on terms.** The reader is a competent programmer who is not a
physicist, a graphics programmer or a Kerbal player. A term such a reader would
not already know is defined where it is first used: in this file by the gloss in
_Defines_, and in the lessons by the lesson that owns it, in the sentence where
it first appears. A later lesson that uses the term links to the owner rather
than defining it again. Ordinary programming vocabulary — cache, thread, JSON,
module — is not defined.
